# Acceptance criteria

One file per layer. Each criterion is written as Given / When / Then so it can become a test first (TDD).

## Turning a criterion into a test

**Framework: Spock `2.5-groovy-5.0`** (`spock-core` + `spock-spring`) on **Spring Boot 4.1.3**.
- Spock 2.5 (6 Oct 2026) added Spring 7 support.
- Boot 4.1 manages Groovy 5.0.8, which the `groovy-5.0` build matches.
- Boot 4.1 brought back the Spock integration that 4.0 had removed (spring-boot#48513).
- Spock 2.5 runs on JUnit 6, which Boot 4.1 manages.
- In Spring tests, use Spock's `@SpringBean`, not `@MockitoBean`.
- Don't use `testcontainers-spock` 2.0.5: it's built against Spock 2.3 / Groovy 4. Containers are Spring `@Bean`s instead.

- **One feature method per criterion, named after its id:** `def "API-01 rejects an upload #variant the X-User-Id header"()`. Test reports then line up with these files.
- **The Given / When / Then sentences go verbatim into the block labels** (`given: "…"`, `when: "…"`, `then: "…"`, `and: "…"`), with the code for each sentence right underneath.
- **Scenario tables (`where:` in the criteria) become Spock data tables;** each row runs and reports as its own test.
- **Mocks:** Spock's own (`0 * fileService._` = never called). In Spring tests, `@SpringBean` replaces a bean with a Spock mock (e.g. the file service in HTTP API tests).
- **Not chosen:**
  - Cucumber, where `.feature` files are the tests: it needs a step-definition glue layer and a second framework for low-level tests.
  - JUnit 5 with `@DisplayName`: natural language only in names.
  - Cucumber stays the option if non-developers need to read and run the specs.

## Scope rule

A criterion asserts only what its own layer decides.
- HTTP API criteria treat the core as a black box called **the file service**. They cover:
  - what the HTTP layer accepts or rejects;
  - what it hands to the file service;
  - how the file service's answers and failures become HTTP responses;
  - connection behaviour.
- Duplicate rules, cleanup and storage effects are asserted in Domain and Storage. They are never asserted in HTTP API.

## Ids and tags

- Ids never change once agreed; retired criteria are struck through, not renumbered.
- **[BRIEF]** marks a test the brief explicitly requires.

## Test levels

- **Controller:** MVC slice (MockMvc), file service faked. Validation and response mapping. Can't carry large bodies: MockMvc holds the body as a `byte[]`, and a Java array can't even hold 2 GiB.
- **HTTP:** app on a real port with real embedded Tomcat, file service faked; no database, no object store. Streaming, `Expect: 100-continue`, timeouts, disconnects.
  - The app and the specs share one JVM, so its heap limit applies to both.
  - Runs in its own Gradle test task so its heap setting and slow tests don't affect the fast levels.
- **Integration:** real Mongo and object store in containers. Used by Domain and Storage.
- **Container:** black-box test against the built Docker image with the brief's limits. Used by System.

## Errors (all layers)

Every error response is RFC 9457 Problem Details (`Content-Type: application/problem+json`).
- Our own errors carry a stable full-path `type` (e.g. `/problems/filename-exists`), listed in each layer's file and in the project README. They don't need to resolve to a real page.
- Errors generated by Spring itself (e.g. 415) and 500s use `about:blank`, which RFC 9457 defines as "no additional semantics beyond that of the HTTP status code", with the status phrase as `title`.
- A 500 never exposes internal details.
- Enabled with `spring.mvc.problemdetails.enabled=true`; extra fields go in via `ProblemDetail.setProperty` and are rendered at the top level of the JSON.
